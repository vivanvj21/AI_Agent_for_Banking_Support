# Autonomous Bank Assistant

A multi-agent AI system for banking customer support, built on **LangGraph** with
**Claude** as the core LLM. It answers policy/FAQ questions via semantic search,
looks up account balances and transaction history, and performs security actions
(lock a card, report fraud) — all gated behind a deterministic identity check.

This is a portfolio/demo project. It uses synthetic data and a local SQLite
database; it is not connected to any real banking system.

## Why this architecture

A single agent with every tool bolted on tends to misfire under ambiguity and is
hard to reason about. This system instead uses a **supervisor + 3 sub-agents**
split by *what the tool can do*, not just topic:

- **Search agent** — read-only, no side effects, no auth required.
- **Account agent** — read-mostly (balance, transaction history), requires identity verification.
- **Fraud agent** — state-changing (lock card, report fraud), requires identity verification.

Splitting by blast radius (rather than just "loans vs accounts") is a
defensible engineering reason for the split, not modularity for its own sake.

### The identity verification gate is not an LLM decision

The most important design choice in this system: **identity verification is a
plain Python function invoked as a hard graph edge**, not a tool the LLM can
choose to call or skip. Every path into the account or fraud agents passes
through `verify_gate` in `graph.py`. This is deliberate — it's the answer to
"how do you stop a prompt injection from talking its way past identity
checks": the check is enforced in code, not argued about in a system prompt.

Similarly, `user_id` is **injected server-side** into every tool call inside
`account_agent.py` / `fraud_agent.py` rather than trusted from the LLM's tool-use
arguments — the model never gets a chance to call `get_balance(user_id="someone_else")`,
because the code overwrites whatever it supplies.

Every fraud/account tool also re-checks row ownership in SQL as defense in
depth (see `test_cannot_lock_another_users_card` in `tests/test_tools.py`),
so even a bug in the graph-level gate wouldn't leak another user's data.

## Architecture diagram

```
User message
     |
     v
Supervisor (classifies intent: search / account / fraud / unclear)
     |
     +-- search -----------------------------> Search agent -> search_faq (Chroma) -> END
     |
     +-- account / fraud -> Verify gate (deterministic)
     |                          |
     |                          +-- verified -> Account agent -> SQL (balance, history) -> END
     |                          +-- verified -> Fraud agent -> SQL (lock/report) -> END
     |                          +-- failed (< 3x) -> ask for credentials -> END (waits for next turn)
     |                          +-- failed (3x) -> human handoff -> END, session closed
     |
     +-- unclear -> clarify -> END
```

image viewer — GitHub also renders SVGs inline).

## Embeddings: a note on the vector search tool

Anthropic doesn't provide its own embeddings endpoint, so `tools/embeddings.py`
defines an `EmbeddingProvider` interface with two implementations:

- **`VoyageEmbeddingProvider`** (production default) — real dense embeddings via
  Voyage AI, Anthropic's recommended embeddings partner. Requires `VOYAGE_API_KEY`.
- **`LocalHashEmbeddingProvider`** (offline dev/CI fallback) — a deterministic,
  dependency-free hashing-trick vector. This is explicitly **not** a semantic
  embedding — it's lexical bag-of-words projected to a fixed dimension, useful
  for testing the retrieval plumbing without network access or an API key, but
  it will not generalize past keyword overlap the way a real embedding does.

`get_default_provider()` picks Voyage automatically if `VOYAGE_API_KEY` is set,
otherwise falls back to the local provider with a printed warning. This keeps
the system honestly labeled rather than quietly shipping a TF-IDF-equivalent
as if it were semantic search.

## Failure handling

- **Retry cap**: `verify_gate` tracks `retry_count` in state; after
  `max_retries` (default 3) failed verification attempts, the graph routes to
  `human_handoff` instead of looping indefinitely.
- **Tool failures don't crash**: every tool function returns `{"error": "..."}`
  on expected failure cases (unknown user, wrong PIN, card not found) rather
  than raising — the calling agent sees the error as a tool result and can
  react to it in conversation (e.g. ask again) instead of the process crashing.
- **Irreversible actions require confirmation**: `report_card_lost` is
  permanent, so the fraud agent's system prompt requires it to confirm with
  the user before calling it — `lock_card` (reversible) does not need this.

## What's cut from a "full" production version, and why

- **AWS Lambda / API Gateway**: not implemented. A single Dockerized service
  is a more honest v1 for a solo portfolio project; Lambda is noted here as
  the natural next step rather than half-implemented.
- **CloudWatch**: not wired up. `tool_calls_log` in `agents/state.py` captures
  every tool decision in-process; shipping that to CloudWatch is a
  straightforward next step (a `boto3` `put_log_events` call from the CLI/API
  layer) but wasn't built to avoid a fake integration with no real logs
  flowing anywhere.
- **AutoGen**: not used alongside LangGraph — picking one orchestration
  framework rather than hedging with two was a deliberate scope decision.

## Interview-ready explanations

**How does the agent decide which tool to use?**
The supervisor node classifies intent with a constrained single-decision LLM
call (not free ReAct tool use — it can only return one of four labels). Each
sub-agent then runs its own tool-calling loop against only the tools relevant
to its role, so the model is choosing among 2-5 tools at a time, not 10+.

**How do you handle failures or agent loops?**
Two separate mechanisms: `retry_count` in graph state caps failed
verification attempts before falling back to human handoff; each sub-agent's
tool-calling loop has a `max_tool_iters` cap (default 3) so a confused model
can't loop indefinitely calling tools without producing a final answer.

**Why multiple agents instead of one with all tools?**
Splitting by blast radius — read-only search, read-mostly account, and
state-changing fraud — means a compromised or confused instance of the
lowest-privilege agent (search) has no access to tools that could leak data
or take action. It also keeps each agent's system prompt and tool list small
enough that tool selection stays reliable.
